# 架构决策记录（ADR）

记录"为什么这么设计"，以及被否掉的方案。这类问题比"用了什么技术栈"更能体现工程判断。

---

## ADR-1：AI 只产出声明式用例，不产出代码

**背景**
最初（原方案）是让大模型直接写 `pytest + requests` 脚本。实测问题：
- 语法错误、漏 import、`resp["data"]["items"]` 少一层 → 脚本根本跑不起来；
- 断言写反（`assert code == 1`）→ 跑过了但是假绿；
- 同一需求两次生成结果差异大，无法回归；
- 「脚本报错 → 回灌模型 → 再改」的闭环，本质是在赌模型这次能不能蒙对。

**决策**
模型只输出 JSON 用例：`{action, payload, expect, snapshot, wait_async}`；
脚本由 `m2_automation/renderer.py` 用固定模板渲染，断言逻辑收敛到模板内的 DSL。

**后果**
- ✅ 代码层零幻觉：渲染出的脚本必然语法合法、断言格式统一；
- ✅ 可回归：同一用例永远渲染出同一脚本；
- ✅ 可评审：QA 看 JSON 就能 review，不需要读 Python；
- ⚠️ 代价：表达力受 DSL 限制（不支持循环、随机、复杂状态机）。缓解方式：DSL 支持 `delta`/`len`/`ne` 等常用算子，复杂场景允许人工补 handler，但仍需过预检。

## ADR-2：契约前置（api_catalog 作为唯一事实源）

**背景**
原方案里，用例生成、脚本执行、Mock 服三处各自维护接口名，极易漂移：
生成用 `/api/gacha/draw`，Mock 服实现成 `/api/draw`，测出来的"失败"全是假的。

**决策**
`app/api_catalog.py` 定义全部接口（method、path、必填字段、取值约束、是否异步、是否需要鉴权）。
Mock 服按它实现，生成器把它写进提示词，校验器用它判定幻觉，渲染器用它拼请求。

**后果**
- ✅ 一处改动，全线跟随；
- ✅ 幻觉检测天然成立（不在目录里 = 不存在）；
- ⚠️ 代价：新增接口必须先改契约。这是有意为之——契约变更本来就该是显式动作。

## ADR-3：失败分类规则化，大模型只做表达

**背景**
"区分业务 bug / 环境脏数据 / 脚本问题"如果交给模型，会有三个问题：
结论不稳定（同一条日志两次结论不同）、无法单测、无法解释（开发会问"凭什么"）。

**决策**
`m3_defect/classifier.py` 用有序规则判定，关键洞察是**看断言期望与实际的方向**：

| 现象 | 判定 | 依据 |
|---|---|---|
| 期望 `code=0`，实际 `1003`（资源不足） | 环境/脏数据 | 前置资源没造出来，不是产品缺陷 |
| 期望 `code=1005`（幂等拦截），实际 `0` | 业务缺陷 | 幂等保护缺失，是**真 bug** |
| 期望 `1003`，实际 `0` | 环境 | GM 指令没生效，资源根本没置低 |
| 业务字段值不符（`rarity` 期望 SSR 实际 R） | 业务缺陷 | 行为与需求不符 |
| `NameError` / `SyntaxError` | 脚本问题 | 与产品无关 |

**后果**
- ✅ 每条结论都能指到具体日志特征；
- ✅ 分类逻辑可单测（12 条用例覆盖各类分支）；
- ⚠️ 代价：新失败模式需要补规则。兜底为 `UNKNOWN` 转人工，不硬猜。

## ADR-4：自愈必须有边界

**背景**
"AI 自动修复失败用例"听起来很美，但如果让模型看到 `AssertionError` 就改断言，平台会永远全绿——**缺陷被 AI 掩盖**，这比没有自动化更危险。

**决策**
自愈入口只有一个：`kind == SCRIPT_ERROR`。且修复后必须重新通过 AST 预检才允许执行。
修复策略规则优先（补 import、修标识符笔误，覆盖高频错误），未命中才用模型。

**后果**
- ✅ 业务缺陷不可能被"修"掉；
- ✅ 高频错误零成本、确定性修复；
- ⚠️ 代价：规则库需要持续积累（当前 3 条规则，覆盖 Demo 中 100% 的脚本错误）。

## ADR-5：异步断言统一走轮询，不用 sleep

**背景**
游戏发奖走 MQ/定时任务，`settle` 后奖励状态是 `pending`，1~2 秒后才 `claimable`。
`time.sleep(3)` 的问题：环境慢时误报（假失败），环境快时白等（执行时间翻倍）。

**决策**
统一 `_wait_until(fetch, spec, timeout=2×SLA, interval=0.4)`：轮询到断言通过或超时，
超时抛 `AssertionError` 并被分类器识别为 `ASYNC_TIMEOUT`（而不是业务 bug）。

**后果**
- ✅ 消除异步误报，执行时间随环境自适应；
- ✅ 超时被单独归类，避免"异步慢"被误判成"业务错"。

## ADR-6：数据集从被测服实采 + 难度断崖检测

**背景**
体验分析如果拿公开数据集或用随机数，一句话就问穿。而"哪关最难"这种结论，
只看通关率最低会误判——后期关卡天然更难，通关率低不代表设计有问题。

**决策**
1. 采集走真实接口：每个测试账号实际执行 进入→结算→领奖，行为数据落库；
2. 分析看**相邻关卡的跃迁**：`drop = clear_rate[i-1] - clear_rate[i] >= 0.15` 判定难度断崖；
3. 结论必须绑定数据证据（关卡号 + 指标数值），禁止空泛建议。

**后果**
- ✅ 能定位"数值抄错"的位置（Demo 中第 6→7 关、11→12 关）；
- ⚠️ 代价：采集耗时随账号数线性增长。缓解：小样本抽样实跑 + 分布仿真补齐，UI 上明确标注模式。

## ADR-7：SQLite 默认 + MySQL 可选

**决策**：`db.py` 做方言适配（`?` → `%s`、DDL 类型映射），业务 SQL 只写一份。

**理由**：`git clone` 后能直接跑，比"生产级 MySQL 部署"重要得多；
真实项目里换成 MySQL 只需改 `QA_DB_URL`。

**代价**：没有连接池、没有迁移脚本、`?` 占位符替换是简单字符串替换（若 SQL 里出现字面量 `?` 会有问题）。演示足够，生产需补 Alembic/Flyway。

## ADR-8：为什么拆一个 Java 编排层（以及为什么只拆这一层）

**背景**
默认形态是 Python 单栈：`pipeline.run_batch()` 串行跑用例，一条命令跑通，够用。
但真实 QA 场景是十个人并发提交、每人几十条用例，此时会立刻暴露：无并发上限、任务状态不一致、
重复提交被执行两次、提交错了没法停、跑完不知道进度。

**决策**
只把「调度」这一层切出去，用 Spring Boot 实现：

| 关注点 | 实现 | 为什么不用 Python 做 |
|---|---|---|
| 并发上限 | `ThreadPoolTaskExecutor(core=max=3)` + 有界队列 + `AbortPolicy` | 不是做不到，而是线程池/队列/拒绝策略在 JVM 侧是标准件 |
| 状态一致性 | DB 级 CAS：`UPDATE ... WHERE status='PENDING'` + 枚举状态机 | 需要一个强类型的、可被编译器检查的状态定义 |
| 幂等 | `clientRequestId` 应用层判重 + 数据库唯一约束兜底 | 二次兜底依赖数据库约束语义，JPA 侧更自然 |
| 可取消 | 只取消 PENDING，不打断 RUNNING | 需要明确的"什么状态允许什么操作"的矩阵 |
| 派发时机 | `TransactionSynchronization.afterCommit()` | 事务边界是 JPA 的一等公民 |

Python 侧只加一个无状态执行器（`app/worker_api.py`），暴露"执行单条用例"的 HTTP 接口。

**为什么不整个换 Java**
Python 的 AI 生态（LLM SDK、pandas、pytest）是这个项目的半条命，硬换等于砍掉模块 1 和 4。
所以按**能力归属**切分：AI 与数据留 Python，并发与一致性放 Java，中间用 HTTP 契约隔离。

**后果**
- ✅ 两种语言各做擅长的事；执行器无状态可多实例，Java 侧只改 `worker-base-url`；
- ✅ 不启动 Java 也能完整演示，`run_demo.py` 完全不受影响（可选加速层）；
- ⚠️ 代价：多一套构建工具链（JDK+Maven）、跨进程调试更麻烦；
- ⚠️ 已知不足：H2 内存库重启丢任务、无持久化队列、不做失败重试（重试语义属于执行层自愈，调度层重试会放大故障）。

## 分层原则

```
UI (m5_ui)  → 展示与交互，不含业务逻辑
pipeline    → 编排（唯一入口，UI/CLI/CI 共用）
m1~m4       → 领域能力，彼此不横向依赖（m2 只依赖 m3 的 classifier）
repository  → 唯一写 SQL 的地方
db/config   → 基础设施
```

约束：**任何模块都不 import `m5_ui`**；**UI 不直接调 m1~m4**，只调 pipeline。
这样"页面能做的事，命令行和 CI 也能做"，也方便后续接 CI 定时回归。

跨语言边界（Python ↔ Java）只有一种形式：**HTTP + JSON 契约**。
Java 不认识 Python 的类，Python 也不需要知道调用方是谁 —— 这条边界让两侧可以独立演进、
独立扩缩容，也方便将来把执行器换成 Go 写的实现。
