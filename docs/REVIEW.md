# 自审记录（方案评审 → 实现 → 审查 → 修正）

按"方案 → 实现 → 自动审查 → 修正 → 下一阶段"推进，下面是被发现并修掉的问题，
以及方案层对原始设计的改动。**这份记录本身就是工程证据**——它证明代码是审出来的，不是一次写对的。

---

## 一、方案层：对原始设计的 8 处改动

| # | 原始设计 | 改动后 | 原因 |
|---|---|---|---|
| 1 | 模块2「AI 生成 pytest 脚本」 | AI 只产出**声明式用例 JSON**，脚本由模板确定性渲染 | AI 写的代码语法/import/断言都不可控，"回灌修复"本质是赌模型；渲染器让代码层零幻觉、可回归 |
| 2 | 各模块各自定义接口 | `api_catalog.py` 作为**唯一事实源**，Mock 服/生成/校验/渲染全读它 | 原设计接口名三处各写一遍，必然漂移，导致大量"假失败" |
| 3 | 「区分三类失败」交给 AI | **规则优先**（可解释/可单测/可回归），LLM 只做缺陷描述润色 | 模型分类不稳定且无法解释，开发会追问"凭什么说是环境问题" |
| 4 | 依赖真实大模型 API | **可插拔 LLM + 离线规则引擎兜底** | 现场断网/额度耗尽会直接翻车；离线还能省成本 |
| 5 | MySQL | **SQLite 默认 + MySQL 可选**（方言适配） | clone 下来能直接跑，比"生产级部署"重要 |
| 6 | 「自动返回给 AI 迭代修复脚本」 | **自愈只允许修脚本自身错误**，业务缺陷一律开单 | 原设计最危险的漏洞：让 AI 看到断言失败就改断言，平台永远全绿，缺陷被掩盖 |
| 7 | 体验分析只有「卡点分布/难度曲线」 | 增加**难度断崖检测**（相邻关卡通关率跃迁） | 只看"通关率最低"会把设计意图误判成 bug，看跃迁才能定位数值抄错的位置 |
| 8 | 未体现"版本验证" | 增加**回归基线对比**（本批 vs 上批：新增失败/已修复/持续失败） | 岗位要求里的版本验证，原方案缺这一环 |

额外补齐：原设计没有"构造边界数据"的手段，新增 `/api/admin/{pity,grant,bag_fill}` GM 指令——
这是游戏 QA 的真实工作方式（要找保底边界，必须有办法把计数置到 89）。

## 二、实现阶段：自动审查抓出并修掉的 28 个问题

### 致命级（会导致功能不正确）

**1. 去重算法误杀幂等用例**（`schema.py`）
- 现象：`奖励重复领取只发一次` 被判为 `通关后异步奖励到账` 的重复用例，模拟度 1.00。
- 根因：用**步骤集合**算 Jaccard，重复的第二次 `claim` 被集合去重，两者集合完全相同。
- 修正：改为 `Counter` **多重集** Jaccard（交/并都按出现次数计）。
- 影响：这条用例正是抓"重复发奖"缺陷的那条，漏掉就等于漏掉一个真 bug。

**2. 校验规则误伤边界用例**（`validator.py` R4）
- 现象：`保底计数89时下一抽必出SSR` 被判"没有断言非 0 错误码"→ 不合格。
- 根因：把"非正向用例"一律当成"反向用例"，要求必须断言错误码。
- 修正：拆成两类语义——反向用例断言非 0 错误码；边界用例允许断言**边界值**（`rarity=SSR` / `delta:-160` / `len:0`）。

**3. 自愈规则把"自己"当成候选**（`healer.py`）
- 现象：`NameError: name '_check'` 无法修复，直接落到 LLM。
- 根因：候选集里包含 `KNOWN_SYMBOLS`，其中就有 `_check` 本身，相似度 1.0 命中自己，替换后代码没变化被判"未修复"。
- 修正：候选集排除掉待修复标识符本身。

**4. 自愈演示其实是假通过**（`pipeline.py`）
- 现象：注入故障后脚本仍 100% 通过。
- 根因：`str.replace("_check(body", "_chek(body")` 没限次数，把**函数定义**和**调用点**一起改名了，脚本自洽。
- 修正：只改 `def _check(body`（定义），调用点保持原名 → 运行时抛 NameError，真实触发自愈链。

**5. 缺陷单重现步骤带脏变量**（`analyzer.py` / `offline.py`）
- 现象：重现步骤写成 `account=$account`，开发照着复现不了。
- 修正：把真实测试账号注入到步骤渲染里。

**6. 断言解析正则跨行贪婪**（`classifier.py`）
- 现象：`实际 'R'` 后面把整段 traceback 都吞进 `actual`，污染分类判断。
- 修正：`([^\n]*)` 限制到单行，去掉 `re.S`。

### 工程级（会导致偶发故障/难排查）

**7. runner 查脚本记录的顺序错了**（`runner.py`）
- 原逻辑先 `latest_script(case_id)` 再 `save_script`，导致 run 记录关联的是**上一次**的脚本。
- 修正：先存本次脚本快照，再建 run 记录 —— 顺带获得"能精确复现当时跑的哪版脚本"的能力。

**8. 环境初始化返回的 ok 恒为 True**（`env_manager.py`）
- `any("失败" not in x for x in log)` 这种写法只要有一行不含"失败"就为真，等于没判断。
- 修正：显式布尔累积。

**9. MySQL 分支会失效**（`db.py`）
- `query()` 在 `with` 块外访问 `cur.description`，SQLite 分支侥幸没走到，MySQL 分支会抛异常。
- 修正：把 `description` 收进 `with` 块内。

**10. 自愈演示结果判定靠字符串匹配**（`pipeline.py`）
- `"PASS" in steps[-1]["detail"]` 这种判定一旦文案改了就会误判。
- 修正：改用显式 `passed` 布尔。

### 低级但必须记（说明检查手段有效）

**11. `api_catalog.py` 语法错误**：`ApiSpec("GET", "/api/bag", "…", summary_ok := "…")` —— 关键字位置用海象运算符，Python 不支持。被首次导入直接暴露。

**12. `offline.py` 三处列表缺 `}`**：`steps=[{...}, {...}, ]` 少一个闭合括号，被 `python -m compileall` 一次性抓出（这也是为什么我要在流程里加编译检查）。

**13. 测试夹具自己写错了**：PRD 夹具里没有"保底"二字，却断言 `"保底" in hits` —— 测试失败暴露的是**夹具不真实**，顺手把夹具改成更贴近真实 PRD 的写法。

### 加入 Java 编排层后新暴露的 5 个问题

**14. JDK 版本不一致导致服务起不来**（`pom.xml` / 启动脚本）
- 现象：`java -jar` 直接抛 `UnsupportedClassVersionError: class file version 65.0`。
- 根因：`mvn` 用 `JAVA_HOME`（JDK 21）编译，而 `PATH` 上的 `java` 是 17，字节码版本不兼容。
- 修正：pom 目标降到 **17**（Spring Boot 3.x 的 LTS 基线，17/21/24 都能跑）；
  启动脚本同时改成"显式挑一个 ≥17 的 JDK 并打印出来"，避免构建与运行用两个 JDK。

**15. 端口 8080 被环境里的代理占掉**（`application.yml` / 启动脚本）
- 现象：Spring 报 `Port 63749 was already in use`（错误信息还误导成随机端口），
  但 `curl 127.0.0.1:8080` 返回 **502** —— 说明 8080 上蹲着代理。
- 定位方式：换 `--server.port=18080` 手动启动，服务立刻正常 → 确认是端口被占而非配置问题。
- 修正：默认端口改 18080 并在脚本里显式传 `--server.port`（命令行参数优先级最高）。

**16. SQLite 并发写偶发 `attempt to write a readonly database`**（`db.py`）
- 现象：Java 3 路并发调执行器时，15 条用例里有 1 条被判 `WORKER_ERROR`（不是业务失败，是执行器内部错）。
- 根因：我在**每个连接**上都执行了 `PRAGMA journal_mode=WAL`。这个 pragma 需要独占锁，
  并发连接互相打架时会报 read-only；连日志都显示 WAL 文件根本没建出来。
- 定位方式：写了一个 6 线程 × 15 次写的探针，稳定复现 2/90 失败。
- 修正：WAL 只在初始化时设一次（它是数据库级持久设置，本来就不该每连接设），
  连接只设 `busy_timeout`，并给写操作加指数退避重试（只重试 4 类瞬时错误）。
  修完探针 0 错误，Java 全量 15 条跑 3 轮无 WORKER_ERROR。

**17. Windows 上裸调 `mvn` 抛 FileNotFoundError**（`scripts/demo_java_orchestrator.py`）
- 根因：Windows 里可执行文件是 `mvn.CMD`，`subprocess.run(["mvn", ...])` 找不到。
- 修正：`shutil.which("mvn")` 解析出全路径再调用（顺带兼容 `mvn.cmd` / `mvn.bat`）。

**18. 并发下同一用例的脚本文件会互相覆盖**（`renderer.py` / `runner.py`）
- 场景：两个批次同时调度同一条用例，都会写 `test_01_<caseId>.py`，可能一个进程正在跑、
  另一个把它覆盖了，报错信息会莫名其妙。
- 修正：`renderer.write_script(..., tag=batchId)` 给文件名加批次后缀；并发路径才需要，串行不受影响。

### 接入真实大模型（阿里云百炼 qwen-plus）后新暴露的 8 个问题

这一轮是"仿真测试"永远发现不了的：离线模板是我自己写的，所以用例天然合规；
换成真实模型后，信息缺口立刻变成 bug。**根因几乎都不是模型笨，而是我没把契约说全。**

**19. 模型把 `repro_steps` 返回成 JSON 数组，直接写库崩溃**（`m3_defect/analyzer.py`）
- 现象：`sqlite3.ProgrammingError: Error binding parameter 8: type 'list' is not supported`，整批任务中断。
- 根因：离线模板返回字符串，模型返回数组；数据层直接绑参，类型没校验。
- 修正：新增 `app/llm/normalize.py`（`as_text` 把数组/字典铺平成可读文本），
  分析层与建议层都先归一化；数据层再加一道 `_text()` 兜底，保证脏类型不会击穿 SQL。

**20. 提示词没写 `$battle_id` 这套变量约定 → 模型编造 ID**（`llm/prompts.py`）
- 现象：`battle_id="BATTLE_5_123456"`，执行时必然「对象不存在」，**15 条里 11 条被误判成环境问题**。
- 根因：`$变量` 是我在渲染器里实现的约定，但没写进提示词——模型只能靠猜。
- 修正：提示词显式声明 `$account` / `$battle_id` / `$reward_id` 及其来源接口，并给完整的异步链路示例。

**21. 提示词没说 `delta` 必须与 `snapshot` 同步骤**（同上）
- 现象：模型把 `snapshot:["gems"]` 写在查询步骤、`delta:-160` 写在抽卡步骤，断言永远缺快照。
- 修正：提示词明确"同一步骤"，并加规则 **R10** 在用例层拦下。

**22. 契约只有入参、没有响应体 → 模型开始编字段名**（`api_catalog.py`）
- 现象：断言了 `data.bag_used`、`data.mail_pending`、`data.pity_pool_featured`、`data.items`（结算接口），
  执行时全是 KeyError，浪费一整轮执行。
- 根因：契约表只声明了请求字段，模型不知道响应长什么样，只能按常识猜。
- 修正：**把契约做成双向** —— `ApiSpec.response` 声明每个接口 `data` 下的字段，写进提示词，
  并加规则 **R11**：断言路径的顶层字段必须在响应契约里，否则直接判不合格。

**23. 分类器优先级错：把「对象不存在」判成业务缺陷**（`classifier.py`）
- 现象：期望 1005、实际 1004（对象不存在），被判成"幂等保护缺失"的 S2 业务缺陷。
- 根因：只看"期望 vs 实际不相等"，没先看实际错误码的语义。
- 修正：**先按实际错误码归类** —— 1002/1003/1004 一律视为环境/数据问题，再谈期望值。

**24. 时序类断言被误判成业务缺陷**（`classifier.py` + `validator.py`）
- 现象：断言 `data.status == "pending"`，实际已流转为 `claimable`，被记成业务缺陷（假阳性）。
- 修正：加规则 **R12**（断言瞬时状态 → WARN，提示改用 `wait_async` 轮询）；
  分类器识别"期望 pending / 实际 claimable"→ 归为用例时序设计问题。

**25. 断言正则覆盖不到"长度期望"文案**（`classifier.py`）
- 现象：`data.items 长度期望 0，实际 1` 匹配不上 `期望 X，实际 Y`，落到 UNKNOWN（人工确认）。
- 修正：正则兼容 `长度期望` / `期望变化` 两种修饰词。

**26. 被测服异步延迟与 PRD 不一致，造成随机假阳性**（环境配置）
- 现象："未到账时提前领取"时好时坏——Mock 服实际跑的是 0.5s 延迟，而 PRD/env 写的是 1.5s。
- 修正：把 Mock 服延迟对齐到 PRD 的 1.5s 后重跑，误判消失（14/16 通过，2 张缺陷单全部指向真实注入缺陷）。
- 教训：**测试环境的时序参数必须与需求文档一致**，否则自动化会稳定地骗你。

**27. 数据采集把被测服的异步延迟改了却没还原**（`m4_analytics/collector.py`）
- 现象：同一批用例跑第一遍 75%、跑第二遍还是 75%，"奖励未到账时领取应返回 1005"稳定失败。
- 根因：采集为了让轮询快点，把被测服 `reward_delay` 调成 0，**结束后没还原**。
  于是后面所有"未到账"类断言都失效，被判成业务缺陷（假阳性）。
- 修正：采集前读当前值、`try/finally` 里原样还原。修完重跑 80%，4 张缺陷单全部是真缺陷。
- 讽刺点：**这正是平台自己在模块 3 里警告的"环境脏数据"，结果我先犯了一遍。**
  所以执行器的每一条用例前后都要重置账号，采集器这种"临时改环境"的动作也必须配对还原。

**28. 换成推理模型后"正文为空"**（`llm/client.py`）
- 现象：`deepseek-v4-pro` 返回 200，但 `content` 是空字符串。
- 根因：推理模型先输出 `reasoning_content`，`max_tokens` 太小时预算全被推理吃掉。
- 修正：新增 `LLM_MAX_TOKENS`（默认 8192）并显式下发；空正文时把 `finish_reason` 和推理长度带进错误信息，
  一眼能看出是"被截断"还是"模型没回"。

**顺带产出：4 条新校验规则**

| 规则 | 拦什么 | 触发过的真实问题 |
|---|---|---|
| R9-变量引用 | 动态 ID 写死 / 缺前置步骤 | `battle_id="BATTLE_5_123456"` |
| R10-快照断言 | delta 与 snapshot 不同步骤 | 断言永远缺基准值 |
| R11-响应字段 | 断言了响应里没有的字段 | `bag_used` / `mail_pending` |
| R12-时序断言 | 断言瞬时状态 | `status=pending` 随机失败 |

**效果对比（同一套 PRD）**

| 指标 | 离线规则引擎 | qwen-plus | deepseek-v4.1-flash |
|---|---|---|---|
| 用例有效率（质检通过率） | 100%（模板人工编写） | 80%（16/20） | **100%（20/20）** |
| 平均质量分 | 100 | 93.1 | **95.2 / 97.6** |
| 执行通过率 | 86.7%（13/15） | 87.5%（14/16） | 80%（16/20） |
| 抓到缺陷 | 2 类 | 1 类 | **2 类（4 张单）** |
| 生成耗时（20 条） | <1s | ~147s | ~131s |

结论有三层：
1. 真实模型能把"用例设计"做宽（覆盖更多边界），**deepseek-v4.1-flash 在这套提示词下已经做到 100% 有效**；
2. 但通过率低一点（80% vs 86.7%）不是变差——它从"pity 未归零"和"already_claimed 未置真"两个角度
   同时抓到了同一个注入缺陷，**覆盖更狠**；
3. 提示词与契约的质量直接决定模型表现：qwen-plus 那 20% 的失败全是我没写清契约导致的，
   补全 R9-R12 与双向契约之后，换成 deepseek 就是 100%。

## 四、已知未完成（诚实清单）

1. **并发**：Mock 服用线程锁模拟，未做真实并发压测（幂等缺陷是顺序重复领取，不是真并发）；
2. **概率分布**：保底用确定性随机以便稳定复现缺陷，不代表真实掉率；
3. **数据库**：无连接池、无迁移脚本；`?`→`%s` 是简单替换；
4. **DSL 表达力**：不支持循环/随机/多账号对拍，复杂玩法需人工补 handler；
5. ~~LLM 路径未做端到端联调~~ → **已完成**（阿里云百炼 qwen-plus），过程中又修了 8 个问题，见第二节；
   仍需注意：真实模型的用例有效率（80%）低于人工模板，复杂玩法（活动/社交）尚未验证；
6. **采集性能**：账号数线性增长，百万级需要预聚合表 + 列存；
7. **编排层持久化**：任务存在 H2 内存库，进程重启丢任务；生产需 MySQL + 持久化队列（RabbitMQ/Kafka）；
8. **编排层无重试**：失败即终态，重试语义目前只在执行层（自愈）里，调度层重试会放大故障，需谨慎设计。
