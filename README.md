# AI 辅助游戏玩法自动化校验 & 体验分析平台

> 面向游戏功能/玩法测试：**AI 生成用例 → 契约校验过滤幻觉 → 确定性渲染脚本 → 自动执行 → 缺陷归因 → 玩法体验数据分析**，一个平台覆盖游戏 QA 的日常闭环。

核心覆盖：需求理解、用例设计、自动化脚本、缺陷分析、AI 提效、数据分析、玩家体验优化、版本验证。

---

## 一、这个项目的核心主张

大部分"AI + 测试"的 Demo 是：把需求丢给大模型 → 让模型写 pytest → 跑起来报错 → 再让模型改。

**这条路在工程上是不成立的**：模型写的代码有语法错、import 漏、断言写反，自愈循环等于在赌概率，永远无法进入生产。

本项目反过来做——**把 AI 关进笼子里**：

| 原则 | 具体做法 |
|---|---|
| AI 只做语义活 | 模型输出的是**声明式用例 JSON**（接口、参数、期望值），不输出代码 |
| 代码 100% 确定 | 脚本由**模板渲染器**拼装，断言收敛到自研 DSL（`len:` / `delta:` / `ge:` …） |
| 契约驱动 | `api_catalog.py` 是唯一事实源，Mock 服、生成、校验、渲染全部读它，消灭跨模块不一致 |
| 幻觉挡在用例层 | 12 条可单测的校验规则，不合格用例**不入库、不生成脚本**，原因回灌模型重写 |
| 分类靠规则，不靠模型 | 失败三分类是可解释、可回归的规则；模型只负责把结论润色成人话 |
| 自愈有边界 | **只有"脚本自身问题"允许自愈**；业务缺陷一律开单，否则等于用 AI 掩盖 bug |
| 没有 Key 也能跑 | LLM 可插拔 + 离线规则引擎兜底，断网或额度耗尽也能跑完整流程 |

一句话：**AI 的不确定性被限制在"数据层"，工程确定性由平台保证。**

                                                     └───────────────┘

> 需要"多 QA 并发提交 / 几百条用例同时跑"时，再起 Java 编排层，Python 侧无需改动。

## 三、快速开始

```bash
cd game-qa-platform
pip install -r requirements.txt

python run_demo.py          # 拉起被测服 + 打开看板 http://localhost:8501
python run_demo.py --cli    # 不开浏览器，终端跑完整流程并打印结果
python run_demo.py --check  # 环境自检
pytest tests/ -q            # 89 条 Python 单元测试

# 可选：Java 编排层（需要 JDK 17+ 与 Maven）
python scripts/demo_java_orchestrator.py   # 自动编译 + 起服务 + 验证并发/幂等/取消
cd java-orchestrator && mvn test            # 6 条状态机单测
```

看板打开后，点侧边栏 **「🚀 一键跑通全流程」**（约 20~40 秒），四个 Tab 全部有数据。

### 接入真实大模型（可选，已联调验证）

只认 **OpenAI 兼容协议**，所以 DeepSeek / OpenAI / 阿里云百炼 / 自建网关都能用，改三行配置即可：

```bash
cp .env.example .env
# 以阿里云百炼（MAAS）为例：
# LLM_PROVIDER=aliyun-maas
# LLM_API_KEY=sk-ws-xxxx
# LLM_BASE_URL=https://<workspace-id>.cn-beijing.maas.aliyuncs.com/compatible-mode/v1
# LLM_MODEL=deepseek-v4.1-flash
# LLM_MAX_TOKENS=8192        # 推理模型必须给足，否则"推理烧完预算、正文为空"
```

**实测对比（同一套 PRD、同一套提示词）**：

| 模型 | 用例有效率 | 均分 | 执行通过率 | 抓到缺陷 | 耗时 |
|---|---|---|---|---|---|
| 离线规则引擎 | 100% | 100 | 86.7%（13/15） | 2 类 | <1s |
| qwen-plus | 80%（16/20） | 93.1 | 87.5%（14/16） | 1 类 | ~147s |
| **deepseek-v4.1-flash** | **100%（20/20）** | **95.2 / 97.6** | 80%（16/20） | **2 类（4 张单）** | ~131s |

deepseek-v4.1-flash 的有效率最高、覆盖也最全（同一批用例从 2 个角度抓到了两个注入缺陷），
执行通过率低一点恰恰说明它把边界写得更狠。**它还是推理模型**（响应带 `reasoning_content`），
`max_tokens` 给小了会出现"推理烧完预算、正文为空"——这也是 `LLM_MAX_TOKENS` 这个配置存在的原因。

接真模型的过程本身就是一个"把契约补全"的过程，被拦下的用例几乎都在指出**我自己的信息缺口**：

| AI 产出的问题 | 根因 | 补的东西 |
|---|---|---|
| `battle_id="BATTLE_5_123456"`（编造 ID） | 提示词没说有 `$battle_id` 变量约定 | 提示词补变量语法 + **R9-变量引用** |
| `snapshot` 与 `delta` 写在不同步骤 | 提示词没说必须同步骤 | 提示词明确 + **R10-快照断言** |
| 断言 `data.bag_used` / `data.mail_pending` | **契约只有入参、没有响应体** | `ApiSpec.response` 双向契约 + **R11-响应字段** |
| 断言 `data.status == "pending"` 随机失败 | 时序类断言 | **R12-时序断言** + 分类器识别 |

这也是这个项目最想表达的观点：**AI 出错的地方，往往是你没写清楚的地方。**
校验规则不是"防 AI"，而是把团队对系统的隐含认知显式化。

不配 Key 也能跑完整流程：所有 AI 能力自动降级到 `app/llm/offline.py` 的规则引擎，UI 上会标注当前引擎。

## 四、五大模块

### 模块 1：AI 需求解析 & 用例自动生成
- 结构化解析 PRD：识别玩法领域（卡池/关卡/背包）、**抽取配置数值**（抽卡消耗、保底次数、背包上限）——这些正是边界用例的输入；
- 大模型设计场景，输出**声明式用例 JSON**；
- 12 条硬规则质检（`R1` 结构 / `R2` 接口幻觉 / `R3` 参数契约 / `R4` 断言强度 / `R5` 期望可观测 / `R6` 前置条件 / `R7` 枚举 / `R8` 重复度 / `R9` 变量引用 / `R10` 快照断言 / `R11` 响应字段 / `R12` 时序断言）；
- 风险覆盖矩阵：哪个游戏特有风险（保底计数、异步到账、背包溢出、幂等）没有用例兜底，一眼可见；
- 支持人工编辑，改完立刻重新质检。

### 模块 2：脚本渲染 & 执行引擎
- 声明式用例 → pytest 脚本（确定性模板，AI 不写代码）；
- 断言 DSL：`len:N` / `delta:-160` / `ge:N` / `ne:X` / `not_empty`，配合 `snapshot` 做**精确扣费断言**；
- 执行前 AST 安全预检：语法、危险调用（`os.system`/`eval`/`subprocess`）、依赖白名单、必须含 assert；
- 每条用例独立账号，执行前后自动重置（避免脏数据互相污染）；
- **异步轮询断言**：`_wait_until` 按条件轮询到截止时间，替代固定 sleep，解决 MQ 延迟发奖的误报；
- 自愈闭环：先过确定性规则库（补 import / 修笔误），未命中再走大模型，修完必须重新过预检。

### 模块 3：缺陷采集与根因辅助
- 失败现场自动采集：接口、入参、断言、账号货币/背包状态、时间戳、日志尾部；
- **规则化三分类**：脚本问题 / 业务缺陷 / 环境脏数据 / 异步超时 / 服务端异常 / 用例数据问题；
- AI（或离线模板）产出可直接提交的缺陷单：标题、严重级、描述、重现步骤、根因猜想；
- **版本验证**：本次批次与上一批次对比，输出新增失败 / 已修复 / 持续失败。

### 模块 4：玩法体验数据分析
- 数据**真的从被测服采集**（进入关卡 → 结算 → 领奖），不是凭空随机数；
- SQL 聚合：通关率、平均耗时、平均死亡、失败平均进度、道具使用率；
- **难度断崖检测**：相邻关卡通关率跌幅 ≥15pp 判定为断层——只看"最难关卡"会误判，看"跃迁"才能定位数值抄错的位置；
- 输出带数据证据的体验优化建议 + 可下载 Markdown 报告。

### 模块 5：Streamlit 看板
四个 Tab 覆盖全流程，纯展示层，所有能力 CLI 同样可用。

## 五、实测结果（默认注入 2 个缺陷）

```
用例生成：15 条，质检通过 15 条（有效率 100%）
自动化执行：15 条，通过 13 条，通过率 86.7%
缺陷归因：2 张缺陷单，均归类为「业务缺陷 S2」
  · 保底计数 89 时下一抽必出 SSR → 实际未触发（off-by-one）
  · 奖励重复领取只发一次 → 实际重复发奖（幂等失效）
体验分析：360 场会话 / 24 账号，整体通关率 73.1%，检测到 3 处难度断崖
自愈演示：注入 2 个脚本故障 → 2 轮规则修复 → 通过
幻觉质检：注入 7 条典型 AI 错误 → 7/7 全部拦截

【真实大模型】阿里云百炼 deepseek-v4.1-flash（已联调，非模拟）
  用例生成：20 条 → 20 条通过质检（100%），均分 95.2 / 97.6，耗时 131s
  自动化执行：16/20 通过（80%）
  缺陷归因：4 张单（S1×1 + S2×3），全部指向注入的 2 个缺陷，零假阳性
  体验建议：source=llm，4 条发现 + 4 条建议，每条绑定关卡号与指标数值

【Java 编排层】15 条用例由 Spring Boot 调度、Python 执行
  并发上限 3 → 串行 18440ms / 实际 6906ms，并发收益 2.7x
  幂等：同一 clientRequestId 重复提交 → 返回原批次，不重复执行
  取消：8 条中取消 5 条未开始的，已在跑的 3 条正常完成
  失败分类：13 通过 / 2 业务缺陷（BUSINESS_BUG）原样回传 Java 侧
  Java 调度的批次同样写入 SQLite，可在看板「版本验证」里做跨批次对比
```

缺陷通过开关注入（`MOCK_BUGS`），关掉后 15 条应全绿——这也顺带验证了用例是"可失败的"，不是永远为真的假用例。

## 七、设计取舍

| 问题 | 选择 | 理由 |
|---|---|---|
| 为什么不让 AI 直接写脚本？ | 模板渲染 + 声明式用例 | 代码层零幻觉、可评审、可回归；AI 的价值在场景设计而非语法 |
| 为什么失败分类用规则？ | 规则优先，模型兜底 | 可解释、可单测、可回归；300 条用例全调模型成本与时延都不可接受 |
| 为什么还要做离线引擎？ | 演示稳定性 + 成本 | 现场断网、额度耗尽、CI 环境无 Key 时仍可跑通全流程 |
| 为什么自愈要设边界？ | 只修 SCRIPT_ERROR | 让 AI 看到断言失败就改断言，等于用 AI 掩盖缺陷，这是 QA 的红线 |
| 为什么默认 SQLite？ | 零配置 | 任何人 clone 后能直接跑起来，比"生产级 MySQL"重要，MySQL 一行配置可切 |
| 数据为什么不用公开数据集？ | 从 Mock 服实采 | 证明平台真的打通了被测系统，而不是拿 CSV 做数分 |
| 为什么要拆一个 Java 编排层？ | 并发/状态机/幂等放 Java，AI 与数据留 Python | 单机跑 15 条不需要它；10 个 QA 并发提交、几百条用例同时跑时才需要。按"能力归属"切分而不是按语言偏好 |
| 为什么不直接用 Java 写整个平台？ | 只切调度层 | Python 的 AI/数据生态无法替代，硬换会失去项目一半能力；跨语言靠 HTTP 契约，边界清晰、可独立扩缩容 |

已知限制：
- Mock 服的并发是线程锁模拟，未做真实并发压测；
- 保底概率用确定性随机，只为稳定复现缺陷，不代表真实掉率分布；
- 数据库未做连接池与迁移脚本，演示够用、生产需补；
- Java 编排层用 H2 内存库、无持久化队列，重启丢任务；生产应换 MySQL + MQ；
- 编排层不做失败重试（重试语义属于执行层自愈，调度层重试会放大故障）。

## 八、快速概览

1. **一句话**：把 AI 关进"声明式用例 + 契约校验 + 确定性渲染"的笼子里，让 AI 只做语义活，工程确定性由平台保证。
2. **核心设计点**：用例校验的 12 条规则、失败三分类的判定依据、自愈为什么必须有边界。
3. **演示路径**：点「运行拦截自检」→ 7/7 拦截；点「执行」→ 2 个真实缺陷被抓 + 正确归因 + 自动出缺陷单；点「自愈演示」→ 2 轮修复后通过；跑 `scripts/demo_java_orchestrator.py` → 并发 2.7x + 幂等 + 取消。
4. **踩过的坑**：见 `docs/REVIEW.md`，里面有 10 条真实自审记录。

架构决策见 [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)，实现中的取舍与修正见 [`docs/REVIEW.md`](docs/REVIEW.md)。
